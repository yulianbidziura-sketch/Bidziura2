# VeloUA — навчальна велокрамниця (Spring Boot)

Власний проєкт з дисципліни: заняття 1/1, 1/2, ПЗ 1/3, ГЗ 1/4, ПЗ 1/5, **ПЗ 2/3** і
**ГЗ 2/4**. Предметна область — **велокрамниця**, доменна сутність — `Bike`.

- Стек: **Java 21, Spring Boot 3.4.13, Maven**
- Велосипеди — у **PostgreSQL 16** (у Docker), доступ через **Spring Data JPA**
- Схему й стартовий каталог створює **Liquibase** (`ddl-auto: validate`)
- Перелік віддається **сторінками** (`Pageable` → `Page` → власний `PageDto`)
- **Повнотекстовий пошук** PostgreSQL (`tsvector` + GIN-індекс) замість `LIKE`
- Відгуки — у **MongoDB** (документна база поряд із реляційною)
- Лише backend (REST API), UI додається окремою самостійною роботою

> Сховище в пам'яті з Модуля 1 нікуди не зникло — воно лишилось під профілем
> `inmemory` (`--spring.profiles.active=inmemory`). Той самий API працює на
> обох сховищах, і жоден клас сервісу чи контролера для цього не змінювався:
> підміняється лише реалізація інтерфейсу `BikeRepository`.

## Запуск

1. Підняти бази даних (потрібен Docker):

```bash
docker compose up -d        # PostgreSQL 16 (5432) і MongoDB 7 (27017)
```

2. Запустити застосунок — міграції Liquibase виконаються самі під час старту:

```bash
./mvnw spring-boot:run
```

У логах видно рядки `ChangeSet ... ran successfully` і підсумок `UPDATE SUMMARY`.

Порт застосунку — `8080` (налаштовується в `src/main/resources/application.yaml`).

Корисне:

```bash
docker compose down         # зупинити БД, дані лишаються у томі
docker compose down -v      # прибрати й том: наступний старт створить усе з нуля
./mvnw spring-boot:run -Dspring-boot.run.profiles=inmemory   # без БД, сховище в пам'яті
```

У IntelliJ IDEA: відкрити папку проєкту → дочекатися, доки Maven підтягне
залежності → запустити клас `BikeshopApplication` (зелений трикутник біля `main`).
Докладніше — у файлі `ЗАПУСК-В-IDEA.md`.

Перевірка:

```bash
curl http://localhost:8080/api/bikes
```

Усі приклади запитів — у `requests.md`.

| `PUT` | `/api/bikes/{id}` | оновити велосипед | 200 / 404 |
| `DELETE` | `/api/bikes/{id}` | видалити велосипед | 204 / 404 |

Пагінований перелік повертає `PageDto`:

```json
{ "content": [ ... ], "page": 0, "size": 5, "totalElements": 26, "totalPages": 6 }
```

Параметри сторінки: `page` (з 0, типово 0), `size` (типово 20),
`sort=поле,asc|desc` (можна кілька разів). Приклад:
`GET /api/bikes/page?page=1&size=5&sort=price,desc`.

Помилки повертаються єдиним форматом `ErrorResponse`
(`status`, `error`, `message`, `details`): `404` — немає велосипеда з таким id,
`400` — тіло запиту не пройшло перевірку `@Valid` або в шляху замість числового
id прийшов текст. Приклади — у `requests.md`.

```
    ├── 002-seed-bikes.yaml             20 стартових велосипедів
    ├── 003-seed-more-bikes.yaml        ще 6 (окремим changeSet, не правкою 002)
    ├── 004-view-and-function.yaml      SQL-view bikes_discounted + count_bikes_by_type
    └── 005-fill-missing-photos.yaml    міграція ДАНИХ: UPDATE бракуючих фото
```

Принципи, за якими зроблено поділ:

- **кожен шар — окремий пакет**, на межах шарів стоять **інтерфейси**
  (`BikeService`, `BikeRepository`) — залежності спрямовані на абстракції (DIP);
- **домен не знає про фреймворк** — у класі `Bike` немає жодної анотації Spring;
- назовні віддаються **DTO**, а не доменні об'єкти: внутрішню модель можна
  змінювати, не ламаючи контракт API;
- **вхідний контракт окремо від вихідного**: `BikeRequest` не має поля `id`,
  бо ідентифікатор призначає сервер;
- кожен клас має **одну відповідальність** (SRP): репозиторій зберігає, сидер
  наповнює, маппер перетворює, сервіс виконує логіку, контролер працює з HTTP;
- залежності приходять **через конструктор** (IoC/DI), тому класи легко
  підміняти в тестах.

## База даних і міграції (ПЗ 2/3)

**Схему веде Liquibase, а не Hibernate.** У `application.yaml` стоїть
`ddl-auto: validate`: Hibernate нічого не створює й не змінює, а лише звіряє
наявні таблиці з анотаціями `Bike`. Якщо міграція розійдеться з сутністю —
застосунок не стартує. Єдине джерело схеми — файли в `db/changelog`.

Кожен застосований changeSet Liquibase записує в службову таблицю
`DATABASECHANGELOG`, тому повторний старт нічого не застосовує вдруге
(`Database is up to date, no changesets to execute`). Друга службова таблиця,
`DATABASECHANGELOGLOCK`, не дає двом екземплярам мігрувати схему одночасно.

Перевірити, що схему й дані зробив саме Liquibase:

```bash
docker exec -it veloua-postgres psql -U veloua -d veloua \
  -c "SELECT id, author, filename, orderexecuted FROM databasechangelog ORDER BY orderexecuted;"
docker exec -it veloua-postgres psql -U veloua -d veloua -c "\dt"
```

### Що станеться, якщо змінити вже застосований changeSet

Liquibase тримає **контрольну суму** (checksum, MD5) кожного застосованого
changeSet у колонці `MD5SUM`. Під час старту він перераховує суму з файлу й
порівнює із записаною. Перевірено на практиці — змінив ціну в уже застосованому
`003-seed-more-bikes.yaml` (9800 → 9900) і перезапустив застосунок:

```
ERROR: Exception Primary Reason: Validation Failed:
  db/changelog/changes/003-seed-more-bikes.yaml::003-seed-more-bikes::bidziura
  was: 9:b6cfb0cfdf3b9b3c31f809848a9ac800 but is now: 9:5d4a740d0767e04e1c6169224aa1e9d9
```

Застосунок **не стартує взагалі**: міграції виконуються до підняття
`EntityManagerFactory`, тому падає весь контекст. Чому так і зроблено: на інших
середовищах стара версія changeSet уже відпрацювала, і мовчазна зміна тексту
означала б, що однаковий набір змін дає різні схеми.

**Правило: застосоване не редагують — додають новий changeSet.** Саме тому
додаткові велосипеди пішли окремим файлом `003`, а фото довантажує окремий
`005`, а не правка seed-міграції.

### Стартовий каталог

26 велосипедів: 20 із `002` + 6 із `003`. Оскільки `id` у seed задані явно,
наприкінці кожного changeSet лічильник ідентичності зсувається
(`ALTER TABLE bikes ALTER COLUMN id RESTART WITH 27`) — інакше перший
велосипед, доданий через `POST`, отримав би вже зайнятий `id` і впав на
порушенні унікальності. Перевірено: перший `POST` після міграцій дає `id = 27`.

## Повнотекстовий пошук і MongoDB (ГЗ 2/4)

### Чому `LIKE` замінено на повнотекстовий пошук

Фільтри `?type=` і `?color=` шукають точний збіг, а текстового пошуку в проєкті не було
взагалі. Найпростіший варіант — `LIKE '%текст%'` — як пошук не годиться: він шукає
**підрядок буква-в-букву**, не знаходить за окремими словами в довільному порядку, не
ранжує результати й не може скористатися індексом (повний скан таблиці).

PostgreSQL уміє повнотекстовий пошук вбудовано. Міграція `006` додає таблиці `bikes`
стовпець `search_vector` типу **`tsvector`** — це попередньо оброблений текст, зведений з
моделі, бренду, типу й опису; по ньому створено **GIN-індекс**, а **тригер** перераховує
вектор при кожній вставці чи зміні, щоб нові велосипеди одразу потрапляли в пошук.

Запит виконується нативним SQL (JPQL операторів FTS не має):

```sql
SELECT * FROM bikes
WHERE search_vector @@ plainto_tsquery('simple', :q)
ORDER BY ts_rank(search_vector, plainto_tsquery('simple', :q)) DESC, id
```

`plainto_tsquery` нормалізує введений текст і ставить між словами логічне «І», оператор
`@@` перевіряє збіг документа із запитом, `ts_rank` рахує релевантність для сортування.
Конфігурація **`'simple'`** лише розбиває текст на лексеми без мовного стемінгу: вбудованої
української конфігурації в PostgreSQL немає, а `'english'` зводив би слова до основи за
правилами чужої мови. Наслідок видно на практиці — `карбонова` і `карбоновою` для пошуку
різні слова; це чесне обмеження обраної конфігурації.

Стовпець `search_vector` **не оголошений у сутності `Bike`**: Hibernate у режимі `validate`
перевіряє лише ті колонки, що є в `@Entity`, тож суто службова колонка бази йому не заважає.

Перевірено на живих даних: `?q=Гравійний` → 5 велосипедів, `?q=Kidrex` → 4, два слова
звужують вибірку, порядок слів значення не має, а підрядок (`рам`) не знаходить нічого.

### Чому відгуки — в MongoDB, а не в PostgreSQL

Велосипед має **сталий** набір полів (модель, ціна, розмір рами, кількість швидкостей) —
це добре лягає в таблицю з фіксованою схемою, де кожне поле має тип і обмеження.

Відгук — навпаки, **вільна форма**, яка з часом обростає полями: сьогодні це автор, оцінка
й текст, завтра — фото, відповідь магазину, позначки «корисно», пробіг на момент відгуку.
У реляційній базі кожне таке поле — нова міграція й `NULL` у старих рядках; у документній
колекції документи можуть відрізнятися між собою, і схему наперед оголошувати не треба.
Відгуки до того ж читаються завжди однаково — «усі відгуки одного велосипеда», тобто
складних з'єднань, заради яких беруть реляційну базу, тут просто немає.

Тому в проєкті **polyglot persistence**: велосипеди лишаються в PostgreSQL, відгуки живуть
у MongoDB. Чесно про межі: Mongo програє там, де потрібні транзакції між багатьма
сутностями й `join`, — саме тому каталог туди не переносимо.

**Узгодженість тримає застосунок, а не база.** Поле `bikeId` у відгуку — звичайне поле, а
не зовнішній ключ: Mongo про таблицю `bikes` не знає й прийняла б будь-яке значення. Тому
`ReviewServiceImpl` перед читанням і перед додаванням відгуку перевіряє, що велосипед
існує в PostgreSQL, і кидає `BikeNotFoundException` → `404`. Це ціна підходу: зв'язність,
яку в одній базі забезпечив би зовнішній ключ, тут доводиться писати руками.

Транзакцій для відгуків немає навмисно: кожна операція стосується одного документа, а
запис одного документа в MongoDB атомарний сам собою.

Відгуки оформлені як **під-ресурс** велосипеда (`/api/bikes/{id}/reviews`) в окремому
`ReviewController` — ресурс інший, сховище інше, тож і контролер свій.

Інтеграційні тести йдуть проти **справжніх баз** — `postgres:16-alpine` і `mongo:7`
(ті самі образи, що й у `docker-compose.yml`), які піднімають Testcontainers. Контейнер один на весь прогін — його тримає базовий клас
`AbstractIntegrationTest`. Тест міграцій піднімає **власну** базу, щоб перевіряти
саме стартовий стан і не залежати від тестів, які чистять сховище.

Наскрізні тести **автономні**: `@BeforeEach` очищає сховище (`deleteAll()`),
кожен тест сам створює свої дані через API і бере звідти справжній id, перевіряє
лише те, що створив сам. Стартові дані `BikeSeeder` у тестах не використовуються.

Перевірка автономності — прогін із випадковим порядком методів:

```bash
./mvnw test -Djunit.jupiter.testmethod.order.default='org.junit.jupiter.api.MethodOrderer$Random'
```

**Не покрито — і чому:**

- **конкурентний доступ** (одночасні `POST`/`DELETE` в кілька потоків) — потрібні
  навантажувальні тести; `ConcurrentHashMap` і `AtomicLong` обрані саме заради
  потокобезпечності, але окремо вона не перевіряється;
- **нефункціональні сценарії** (швидкодія, безпека, навантаження) — це інший вид
  тестування й інші інструменти, у Модулі 1 не розглядаються;
- **системний і приймальний рівні** — у проєкті немає UI, а `MockMvc` працює без
  реального Tomcat; наскрізний тест зупиняється на рівні Spring MVC;
- **`405 Method Not Allowed` і `415 Unsupported Media Type`** — їх формує сам
  Spring MVC до нашого коду; свого обробника на них немає, тому й тестів немає;
- **непередбачені `500`** — обробника «на все підряд» свідомо не додано: він
  ховав би справжні помилки під гарним JSON, а на навчальному етапі їх краще
  бачити у стектрейсі;
- **збереження даних між перезапусками** — автоматичного тесту немає (він вимагав би
  перезапуску контексту з тим самим томом), але сценарій перевірено вручну: створений
  через `POST` велосипед (`id = 27`) лишився на місці після зупинки й повторного запуску
  застосунку, і той самий рядок видно в `psql` — розділ 18 у `requests.md`;
- **поведінка при зміні застосованого changeSet** — перевірена вручну (див. розділ про
  міграції): автоматизувати її означало б тримати в репозиторії свідомо зламану міграцію;
- **ранжування `ts_rank` окремим тестом** — перевірено лише те, що релевантніший запис
  знаходиться; порівнювати самі числові оцінки немає сенсу, вони залежать від реалізації
  PostgreSQL;
- **pgvector (векторний пошук)** — на занятті дано оглядово й не входив до обов'язкової
  частини; у проєкті не реалізований.
