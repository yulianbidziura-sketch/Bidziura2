# VeloUA — навчальна велокрамниця (Spring Boot)

Власний проєкт з дисципліни: заняття 1/1, 1/2, ПЗ 1/3, ГЗ 1/4 і ПЗ 1/5.
Предметна область — **велокрамниця**, доменна сутність — `Bike`.

- Стек: **Java 21, Spring Boot 3.4.13, Maven**
- Дані — у пам'яті (`ConcurrentHashMap`), без БД
- Лише backend (REST API), UI додається окремою самостійною роботою

## Запуск

З командного рядка:

```bash
./mvnw spring-boot:run
```

Порт — `8080` (налаштовується в `src/main/resources/application.yaml`).

У IntelliJ IDEA: відкрити папку проєкту → дочекатися, доки Maven підтягне
залежності → запустити клас `BikeshopApplication` (зелений трикутник біля `main`).
Докладніше — у файлі `ЗАПУСК-В-IDEA.md`.

Перевірка:

```bash
curl http://localhost:8080/api/bikes
```

Усі приклади запитів — у `requests.md`.

## Ендпоінти

| Метод | Шлях | Призначення | Код |
|---|---|---|---|
| `GET` | `/api/bikes` | перелік велосипедів (картки) | 200 |
| `GET` | `/api/bikes?type=Гірський` | перелік із фільтром за типом (значення кодується percent-encoding) | 200 |
| `GET` | `/api/bikes?color=Чорний` | перелік із фільтром за кольором (ПЗ 1/3) | 200 |
| `GET` | `/api/bikes?type=...&color=...` | обидва фільтри разом | 200 |
| `GET` | `/api/bikes/{id}` | один велосипед з деталями | 200 / 404 |
| `POST` | `/api/bikes` | створити велосипед | 201 |
| `PUT` | `/api/bikes/{id}` | оновити велосипед | 200 / 404 |
| `DELETE` | `/api/bikes/{id}` | видалити велосипед | 204 / 404 |

Помилки повертаються єдиним форматом `ErrorResponse`
(`status`, `error`, `message`, `details`): `404` — немає велосипеда з таким id,
`400` — тіло запиту не пройшло перевірку `@Valid` або в шляху замість числового
id прийшов текст. Приклади — у `requests.md`.

## Структура (багатошарова архітектура)

```
com.ua.bikeshop
├── domain/               Bike                     — доменна модель, без анотацій Spring
├── repository/           BikeRepository           — інтерфейс сховища
│                         InMemoryBikeRepository   — реалізація в пам'яті
├── service/              BikeService              — інтерфейс бізнес-логіки
│                         BikeServiceImpl          — реалізація
│   └── mapper/           BikeMapper               — домен ↔ DTO
├── web/                  BikeController           — REST-контролер
│                         GlobalExceptionHandler   — @RestControllerAdvice: 404 і 400
│   └── dto/              BikeCardDto              — картка для переліку
│                         BikeDetailDto            — повні дані велосипеда
│                         BikeRequest              — вхідні дані (POST/PUT), без id
│                         ErrorResponse            — єдиний формат тіла помилки
├── config/               BikeSeeder               — стартові дані
│                         WebConfig                — CORS для майбутнього UI
└── exception/            BikeNotFoundException    — 404
```

Принципи, за якими зроблено поділ:

- **кожен шар — окремий пакет**, на межах шарів стоять **інтерфейси**
  (`BikeService`, `BikeRepository`) — залежності спрямовані на абстракції (DIP);
- **домен не знає про фреймворк** — у класі `Bike` немає жодної анотації Spring;
- назовні віддаються **DTO**, а не доменні об'єкти: внутрішню модель можна
  змінювати, не ламаючи контракт API;
- **вхідний контракт окремо від вихідного**: `BikeRequest` не має поля `id`,
  бо ідентифікатор призначає сервер;
- кожен клас має **одну відповідальність** (SRP): репозиторій зберігає, сидер
  наповнює, маппер перетворює, сервіс виконує логіку, контролер працює з HTTP;
- залежності приходять **через конструктор** (IoC/DI), тому класи легко
  підміняти в тестах.

## Тести

```bash
./mvnw test
```

Усього **50 тестів**, усі три рівні піраміди:

| Рівень | Клас | Що перевіряє |
|---|---|---|
| модульний (Mockito) | `BikeServiceImplTest` | логіку сервісу з моканим репозиторієм: правило «порожній фільтр = усі», обидва критерії, 404 на неіснуючий id, збереження id при оновленні |
| модульний | `BikeMapperTest` | перетворення домену в обидва DTO і вхідного DTO в домен |
| модульний | `InMemoryBikeRepositoryTest` | саме сховище: видача id, перезапис за id, фільтри без урахування регістру, порядок за `id`, `deleteById` і `deleteAll` |
| зріз веб-шару | `BikeControllerTest` (`@WebMvcTest`, сервіс замокано) | маршрути, статуси 200/201/204/400/404, структуру JSON, фільтри, єдиний формат тіла помилки |
| наскрізний | `BikeApiIntegrationTest` (`@SpringBootTest` + `MockMvc`, нічого не мокано) | весь ланцюг контролер → сервіс → маппер → сховище, усі шість операцій, 404 і 400 |
| контекст | `BikeshopApplicationTests` | застосунок піднімається |

Наскрізні тести **автономні**: `@BeforeEach` очищає сховище (`deleteAll()`),
кожен тест сам створює свої дані через API і бере звідти справжній id, перевіряє
лише те, що створив сам. Стартові дані `BikeSeeder` у тестах не використовуються.

Перевірка автономності — прогін із випадковим порядком методів:

```bash
./mvnw test -Djunit.jupiter.testmethod.order.default='org.junit.jupiter.api.MethodOrderer$Random'
```

## Звіт про покриття тестами (ПЗ 1/5)

**Покрито** — 50 тестів, по операціях:

| Операція / сценарій | Сховище | Сервіс | Зріз веб-шару | Наскрізний |
|---|---|---|---|---|
| перелік без фільтра | ✅ | ✅ | ✅ | ✅ |
| фільтр за типом | ✅ | ✅ | ✅ | ✅ |
| фільтр за кольором | ✅ | ✅ | ✅ | ✅ |
| обидва фільтри разом | ✅ | ✅ | ✅ | ✅ |
| фільтр без збігів → `[]` | ✅ | — | — | ✅ |
| один велосипед | ✅ | ✅ | ✅ | ✅ |
| неіснуючий id → `404` + тіло | ✅ | ✅ | ✅ | ✅ |
| створення → `201`, id від сервера | ✅ | ✅ | ✅ | ✅ |
| оновлення → `200`, той самий id | ✅ | ✅ | ✅ | ✅ |
| оновлення неіснуючого → `404` | — | ✅ | ✅ | ✅ |
| видалення → `204` | ✅ | ✅ | ✅ | ✅ |
| повторне видалення → `404` | ✅ | ✅ | ✅ | ✅ |
| невалідне тіло → `400` + `details` | — | — | ✅ | ✅ |
| нечисловий id у шляху → `400` | — | — | ✅ | — |
| перетворення домен ↔ DTO | — | ✅ (`BikeMapperTest`) | — | — |
| контекст Spring піднімається | — | — | — | ✅ |

**Не покрито — і чому:**

- **конкурентний доступ** (одночасні `POST`/`DELETE` в кілька потоків) — потрібні
  навантажувальні тести; `ConcurrentHashMap` і `AtomicLong` обрані саме заради
  потокобезпечності, але окремо вона не перевіряється;
- **нефункціональні сценарії** (швидкодія, безпека, навантаження) — це інший вид
  тестування й інші інструменти, у Модулі 1 не розглядаються;
- **системний і приймальний рівні** — у проєкті немає UI, а `MockMvc` працює без
  реального Tomcat; наскрізний тест зупиняється на рівні Spring MVC;
- **`405 Method Not Allowed` і `415 Unsupported Media Type`** — їх формує сам
  Spring MVC до нашого коду; свого обробника на них немає, тому й тестів немає;
- **непередбачені `500`** — обробника «на все підряд» свідомо не додано: він
  ховав би справжні помилки під гарним JSON, а на навчальному етапі їх краще
  бачити у стектрейсі;
- **збереження даних між перезапусками** — сховище в пам'яті, перевіряти нічого;
  цей сценарій з'явиться в Модулі 2 разом із PostgreSQL і Testcontainers.
